# 事件时序约束校验器（Temporal Constraint Checker）

用于**采访证词核对**与**事故复盘时间线分析**的 Web 应用。用户以自然语言形式录入约束：

> 事件 A 比事件 B **早 / 晚** `x` 到 `y` 分钟

再指定一个**锚点事件及其绝对时间**，系统实时将约束转换为**差分约束图**（Difference
Constraint System）并完成：

1. **可满足性实时判定** —— 约束间一旦矛盾（图中出现负环）立即报警；
2. **矛盾环高亮复核** —— 突出显示一条具体的矛盾环：图上红色节点/边、约束列表红色行，
   并逐条列出环上的差分不等式，求和得到 `0 ≤ 负数` 的代数证据，映射回原始证词；
3. **最小修复建议** —— 检测到矛盾时，以每次发现的负环为分支依据搜索
   **停用约束数量最少**的可满足方案；并列最优方案最多展示 5 个并按约束录入顺序稳定排序，
   每个方案列出需停用的约束与修复后的事件时间窗，支持**不写入 localStorage 的一键预览**
   与**确认应用**（确认后批量停用）。搜索累计超过 2000 个状态即停止，并明确标记结果可能不完备；
4. **时间窗计算** —— 可满足时给出每个事件相对锚点的**最早 / 最晚偏移**与对应的绝对时间；
5. **边界依据追溯** —— 对可满足且已设锚点的数据，点击时间窗表中任一事件的最早或最晚时间，
   即展示从锚点推导该边界的**紧约束链**：按推导顺序列出每一步的原始约束、所采用的上界 / 下界
   差分不等式与累计偏移，并在差分图与约束列表中同步高亮（紫色）；锚点事件显示零步证明；
6. **无法定时标记** —— 与锚点在图上没有有向通路的事件标记为「无法定时」；
7. **示例数据 + 本地持久化** —— 内置「事故复盘（可满足）」与「采访证词冲突」两套示例，
   全部编辑内容自动保存在浏览器 `localStorage`（修复预览除外）。

技术栈：React 18 + TypeScript + Vite，纯前端、无后端依赖。

## 一条命令启动

需要已安装 Docker（含 Compose 插件）。在项目根目录执行：

```bash
docker compose up --build -d
```

启动后访问：

> **http://localhost:8080**

镜像构建时会自动完成依赖安装（`npm ci`）与生产构建（`tsc + vite build`），
容器启动即由 nginx 直接托管静态产物，**无需任何额外初始化步骤**。

常用命令：

```bash
docker compose logs -f        # 查看日志
docker compose down           # 停止并移除容器
docker compose up --build -d  # 代码更新后重新构建启动
```

### 修改访问端口

编辑 `docker-compose.yml` 的端口映射，例如改用 9090：

```yaml
ports:
  - "9090:80"
```

然后重新 `docker compose up -d`。

本应用无数据库、无第三方服务、无必需环境变量。可选配置：

## 使用指南

1. **添加事件**：在「事件」面板录入关键时点（如：告警触发、服务恢复）；
2. **指定锚点**：点事件前的单选按钮，或使用顶部「锚点」下拉框，并设置锚点绝对时间；
3. **录入约束**：在「时序约束」面板选择 `事件 A —（早于/晚于）— 事件 B`，
   填写分钟区间 `x ~ y`（要求 `0 ≤ x ≤ y`；`x = y` 表示精确间隔）；
4. **查看实时结论**：
   - 顶部绿色横幅：系统可满足，底部表格给出每个事件的时间窗；
   - 红色横幅：存在矛盾，红色矛盾环给出可逐步复核的不等式链；其下方「最小修复建议」
     给出停用约束最少的方案；
   - 黄色「无法定时」：该事件与锚点之间没有任何约束通路，请补充连接二者的约束；
5. **核对矛盾**：可逐条**取消勾选**可疑证词，观察矛盾环是否消失，快速定位冲突来源；
6. **采纳修复建议**：
   - 点击方案卡片上的**一键预览**：相关约束被临时停用（置灰并标记“预览停用”），
     图与时间窗立即按修复后的状态展示；预览**只存在于内存，不写入 localStorage**，
     可随时「退出预览」返回原数据，任何编辑操作也会自动退出预览；
   - 点击**确认应用**：方案中的约束被**批量停用**并持久化；
   - 并列最优方案超过 5 个时只展示按约束录入顺序最靠前的 5 个（会注明总数）；
     搜索累计达到 2000 个状态仍未结束时，面板会提示**结果可能不完备**。
7. **追溯边界依据**（仅可满足且已设锚点时可用）：
   - 点击时间窗表中任一**可定时**单元格的「最早偏移 / 最早时间」或「最晚偏移 / 最晚时间」
     （带边框、悬停高亮的格子），即在表格下方打开**边界依据追溯**面板；
   - 面板按推导顺序列出从锚点到该边界的**紧约束链**：每一步标明第几步、采用的是原始约束的
     **上界侧还是下界侧**、差分不等式（`t(v) − t(u) ≤ w`）与**累计偏移**；
   - 链上的差分边在图中以**紫色**加粗高亮（终点事件描边加重），对应的原始约束在约束列表中
     同步高亮并标注「追溯第 N 步」；
   - **最早边界**由反向图最短路求得：面板中的边按其在原图中的真实方向（目标 → 锚点）展示，
     但步骤顺序仍按推导顺序（锚点在前）排列，累计偏移取负；
   - **锚点事件**的单元格点击后显示**零步证明**（时间直接由锚点指定，不依赖任何约束）；
   - 「仅单边有界」的无界一侧与「无法定时」事件的格子显示为「—」，**不可点击**，鼠标悬停
     可查看原因（该侧无界 / 与锚点无有向通路）；
   - 再次点击同一格或点击「清除追溯」可取消高亮；**任何编辑、切换锚点或进入修复预览都会
     自动清除旧追溯**——预览中如需追溯，请在预览状态下重新点击，系统按预览后的有效约束重新计算。

### 状态图例（时间窗表）

| 状态 | 含义 |
| --- | --- |
| **锚点** | 时间即用户指定的锚点绝对时间 |
| **可定时** | 最早与最晚偏移都能由约束推出 |
| **仅单边有界** | 只能推出最早或最晚一侧（另一侧无界） |
| **无法定时** | 与锚点无有向通路，图上属于另一连通分量 |

## 算法说明

每条约束 `A 比 B 早 x~y 分钟`（即 `x ≤ t_B − t_A ≤ y`）转换为两条
**差分不等式**，在图中对应两条带权有向边（边 `u → v` 权 `w` 表示 `t_v − t_u ≤ w`）：

- 上界：`t_B − t_A ≤ y` ⇒ `A → B, 权 y`
- 下界：`t_A − t_B ≤ −x` ⇒ `B → A, 权 −x`

`A 比 B 晚 x~y` 时方向互换。

- **可满足性**：差分系统可满足 ⇔ 图中不存在负权环。使用带「超级源点」（全部节点初始
  距离为 0）的 Bellman-Ford 在第 n 轮检测松弛，时间复杂度 O(V·E)，对复盘场景规模足够；
- **矛盾环提取**：从第 n 轮仍被松弛的边沿前驱指针回溯，先走入环内再裁掉环外尾巴，
  得到一条权重之和严格小于 0 的环；
- **时间窗**：以锚点为源跑最短路得到各事件「最晚偏移」`t_i − t_anchor` 的最小上界；
  在反向图上跑最短路得到「最早偏移」。正/反向均不可达即为「无法定时」。
- **边界依据追溯**：最晚边界直接取正向最短路的前驱链（每次松弛实际采用的边），按
  「锚点 → 目标」排列；最早边界在反向图上跑最短路后，将每条反向边按 `constraintId +
  上/下界侧`映射回原图中的差分边，把反向图路径还原为原图中「目标 → 锚点」方向的下界链，
  再反转为推导顺序（锚点在前）、累计偏移取负。由于系统可满足（无负环），前驱链必为简单
  路径，且链上每条边都真实收紧了对应边界——放宽其中任何一条都会改变该边界，故称为
  **紧约束链**。锚点自身为零步证明；该侧不可达（无界 / 无法定时）时不提供追溯。
- **最小修复建议**：在「停用哪些约束可使系统恢复可满足」中求**停用数最少**的方案
  （最小击中集）。采用以负环为分支依据的逐层 BFS（branch and bound）：
  1. 对当前停用集合跑一次 Bellman-Ford；
  2. 若已无负环，当前集合即为可行方案；
  3. 否则任取一条负环 C——任何可行方案都必须再停用 C 上的至少一条约束，
     故只需对 C 上的不同约束逐一分支，完备且不会枚举无关约束；
  4. 按停用数 0,1,2,… 逐层展开，**第一次出现可行方案的层即给出最少停用数**，
     同层全部状态都会被考察，以收集并列最优方案；候选项按约束录入顺序展开，
     同层方案按停用约束的录入顺序字典序稳定排序，最多展示 5 个。

  搜索用全局 visited 集合（停用集合的规范化下标元组）去重；累计访问状态数达到
  **2000** 上限即停止：若已找到方案，最少停用数仍已被证明（但并列方案列表可能不全）；
  若尚未找到方案，则明确标记结果可能不完备。每个候选方案复用 `analyze` 计算修复后时间窗。
